## Objective, why, and boundaries

Build one provider-neutral durable task operation boundary for create (where applicable), read, field/status update, comment, phase handoff, checkpoint, cold resume, and close. Without it, local task files or harness UIs can appear complete while the setup-bound provider has no confirmed state. #177 defines the canonical-provider invariant and five native contracts; #178 supplies the callable adapter boundary, not another tracker.

**In:** binding-validated dispatch, provider-specific identity/status/association/template mappings, native-operation confirmation followed by fresh target readback, idempotent or identity-safe retries, fail-closed actionable errors, and focused offline tests using injected fake provider access. Preserve protected approval gates and ordered phases; do not silently apply approval or move to Done before existing gates pass.

**Out:** harness startup/event wiring and optional local projections (#179), the cross-harness/cold-start E2E provider matrix and journey changes (#180), provider-contract redesign (#177), real production credentials, broad live journeys, GitHub fallback, or a new local task store. The planning turn changes only this document.

## Acceptance criteria (verbatim from #178)

- [ ] Define a provider-neutral interface for reading a task, creating it when applicable, updating fields/status, adding comments, writing phase handoffs, and reading back the durable state.
- [ ] Dispatch exclusively from the generated setup binding and support all catalog providers: Jira, GitHub Issues, GitHub Projects v2 (linked issue plus project item where required), Linear, and custom.
- [ ] Preserve provider-specific identifiers, status mappings, project/board association, and required issue/template semantics without exposing a second tracker abstraction to callers.
- [ ] Make create/update/checkpoint operations idempotent or identity-safe so retries cannot silently create duplicate tasks or split one task's handoff history.
- [ ] Do not report local file or task UI state as successful durable persistence until the bound provider operation and target readback succeed; no local projection is required.
- [ ] Unsupported, unavailable, malformed, or ambiguous provider responses fail closed with an actionable provider-specific continuation and no GitHub fallback.
- [ ] Add focused unit tests with fake provider implementations covering success, retry/idempotency, unavailable provider, failed readback, and unknown identity.

## Minimal implementation design to verify

1. **Location and input:** `src/creator.ts` currently composes `docs/bindings.md` from the chosen `providers/task/*.md` fragment and emits explicit `TASK_TRACKER`, `TRACKER`, and `TRACKER_KEY`. It is a creator path, not the runtime adapter: `src/` is removed from generated projects by `archetype-ownership.json`. Put a small shared runtime boundary in a demonstrably retained/inherited path (or a tested, intentionally packaged runtime path); register any new tracked file in the ownership inventory and update payload identity when implementation needs it. Do not repurpose `src/providers.ts`: it handles agent executable selection/launch, not task persistence. Reconcile generated binding parsing with the actual composed form, not the unbound template or a `.github/` heuristic. Missing/malformed/unsupported `TASK_TRACKER`, `TRACKER`, or `TRACKER_KEY` blocks before dispatch or mutation.
2. **Contract:** give callers one task identity that retains the binding and opaque native identity, plus create/read/mutate/status/comment/handoff/checkpoint/resume/close operations returning only provider-confirmed, freshly read-back state. A handoff carries phase/status, completed work, exact next action, branch/commit, verification, resume evidence and, when blocked, the resume phase and blocker (`templates/handoff.md`). Use explicit operation IDs/correlation and compare native target identity, association, status, and written content on readback; a mutation acknowledgement alone is not success. No local projection is required or authoritative.
3. **Provider implementations:** use injected provider-native access capabilities and small translations, not embedded tokens or an implicit GitHub client. Jira and Linear retain issue key, project/team/board association, native status mapping and provider issue template. GitHub Issues retains repository and issue number, mandatory repository form semantics and native labels/open state. GitHub Projects v2 retains project ID, item ID and, when present/required, verified linked repository issue identity: read back both item status and linked issue/comment. A project-only/draft item must have an actual supported item-native handoff/comment and readback path or block; never fabricate a linked issue. Custom uses only explicitly configured native rules with a supported operation/readback path; otherwise block with the missing capability. Keep protected approval outside routine status changes.
4. **Retry safety:** resolve an existing native identity or unique operation correlation before create or retry; if native create/link/comment is accepted but the response is lost, reconcile by that stable identity and readback before any further write. On missing or multiple matches, unknown write outcome, conflicting target association, or unsupported idempotency, stop with the exact provider/operation/target and evidence needed to resume. Never auto-repeat a possibly accepted non-idempotent mutation or append a handoff to a different task. A duplicate correlation with matching readback returns the same confirmed result; an inconsistent duplicate blocks.
5. **Seams:** #179 will wire harness mechanisms to this interface and handle any optional projections; #180 will prove cross-harness/provider lifecycle scenarios. #178 tests its boundary and five mappings offline, not a claim of live Jira/Linear/custom persistence or a working installed harness.
