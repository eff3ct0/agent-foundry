## Objective, reason, and boundaries

Make the first `@eff3ct/agent-foundry@0.1.0` publication traceable to exactly one final verified `main` commit: `v0.1.0` tag, GitHub Release, npm version, local tarball, registry tarball, payload, and immutable evidence must agree. Automate deterministic release notes/changelog generation and gated GitHub Release creation without letting a draft or dry run publish npm. The existing `release.published` workflow currently publishes the one matching tarball once; it does not create a GitHub Release. Historical tags already claim `v0.1.0`–`v0.2.4`, while the public npm package and `0.1.0` endpoint currently return 404.

In scope: full baseline audit and recheck; owner-confirmed version/history policy; offline changelog and release-creation automation; exact source/package/readback contracts, failure tests, dry-run, package consumer checks and hosted journey evidence; narrowly staged history correction and first publication only after the relevant gates pass. Keep release-only source assets classified as `removed` in `archetype-ownership.json` when they are introduced.

Out of scope: npm unpublish, changing the package name or `foundry` command, broad branding/slug changes (#183), unrelated provider behavior, reading secrets, unreviewed GitHub metadata wording, automatic Template-mode disablement, or using mutable `main` as a substitute for a resolved tag SHA. Do not infer approval to change description, topics, homepage, or slug from #184. Do not perform the owner-reserved final Template-mode change without its own authorization.
