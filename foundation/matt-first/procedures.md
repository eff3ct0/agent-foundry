## 1. Planning — grill-with-docs / wayfinder

**Sources:** [grill-with-docs](skills/matt-pocock/skills/engineering/grill-with-docs/SKILL.md); [wayfinder](skills/matt-pocock/skills/engineering/wayfinder/SKILL.md) only for multi-session decision maps.

- **Inputs:** authorized objective/destination, scope, relevant artifacts, confirmed decisions, standing preferences and actual decision authority.
- **Preconditions:** distinguish unresolved questions from settled answers; do not reopen confirmed decisions merely to interview again. A small change need not create a map.
- **Effects:** inspect/research, ask prerequisite-ready questions, record actual answers or recommendations adopted under an explicit covering delegation; only authorized tracker maps/decision tickets/native relations. Prototypes need their own accepted effects. No implementation by default.
- **Outputs/evidence:** decision detail on its decision ticket, map only a linked gist/fog; Git glossary/ADRs when applicable and authorized. Cite factual support, actual authority and exact provider readbacks; no invented human answer or unvisited necessary decision.
- **Dependencies:** grilling, domain-modeling; research/prototype when relevant (paths below).

## 2. Specification — to-spec

**Source:** [to-spec](skills/matt-pocock/skills/engineering/to-spec/SKILL.md).

- **Inputs:** resolved objective/decisions, scope, observable acceptance scenarios, relevant code/test seams and intended tracker spec identity.
- **Preconditions:** necessary substantive choices settled; seam/granularity decisions answered or explicitly delegated. Reuse an existing canonical spec; no old-chat requirement.
- **Effects:** synthesize/publish/update the agreed tracker specification using bound forms/labels and permitted effects. No automatic implementation or ticket publication.
- **Outputs/evidence:** one canonical tracker spec referencing exact decision resolutions, exclusions/scenarios and pending permissions; exact native identity/content/state read back. No necessary product choice disguised as implementation detail; a spec is not runtime proof.
- **Dependencies:** domain-modeling/codebase-design when relevant.

## 3. Ticketing — to-tickets

**Source:** [to-tickets](skills/matt-pocock/skills/engineering/to-tickets/SKILL.md).

- **Inputs:** accepted spec/plan, scope/criteria, parent, current graph, provider forms/labels and decomposition authority.
- **Preconditions:** vertical units and real prerequisites adopted through actual approval or a delegation covering decomposition; generic implementation authority does not expand scope.
- **Effects:** publish accepted tasks, then native parent/blocker relations after real identities exist. Reuse matching tasks; do not incidentally close/change the source parent or start work.
- **Outputs/evidence:** tasks with criteria, scope, prerequisites and spec pointers; every identity/form/label/edge separately confirmed/read back. Partial publication stays explicit before retry; closed predecessors still need retrievable integrated artifacts.
- **Dependencies:** existing project terminology/architecture where relevant.

## 4. Implementation — implement

**Source:** [implement](skills/matt-pocock/skills/engineering/implement/SKILL.md).

- **Inputs:** exact authorized unit, fresh claim/dependency/checkpoint, spec/criteria, branch/workspace and permitted delivery effects.
- **Preconditions:** valid owner/delegation, actual artifact/integration readiness, accepted workspace conflicts, required verification tools or precise missing gates.
- **Effects:** only in-scope code/docs/tests, appropriate real behavior verification/review and authorized delivery. No protected branch action or extra effect from an upstream commit instruction.
- **Outputs/evidence:** exact Git artifacts and linked checks/review/PR evidence plus confirmed checkpoint/closeout. Applicable behavior must actually run against the identified revision. A commit alone is not Done; missing required checks/review/artifacts/readback keeps work incomplete.
- **Dependencies:** tdd at agreed seams, diagnosing-bugs when needed, code-review; stack/domain tools are explicit external prerequisites when needed, not installed by this catalog.

## 5. Review — code-review

**Source:** [code-review](skills/matt-pocock/skills/engineering/code-review/SKILL.md).

- **Inputs:** resolvable fixed base and exact candidate revision/full diff, originating canonical spec/task and repository standards.
- **Preconditions:** nonempty identified subject and accessible criteria/evidence; read/report-only authority unless fixes separately delegated.
- **Effects:** inspect and report Standards and Spec independently as two axes; persist authorized results, not human approval, merge or completion.
- **Outputs/evidence:** exact base/head/full-diff identity, scope, both axes/findings, limits and next action. Recheck identity before reuse. Parallel reviewers require actual capabilities; explicitly labelled serial adaptation is permitted but cannot satisfy required independent review. Empty diff or absent spec is a stated limit, never a full acceptance claim.
- **Dependencies:** applicable project engineering/security/domain standards; actual independent reviewer capability when required.

## 6. Durable checkpoint — foundry-checkpoint

**Source:** [foundry-checkpoint](skills/foundry-checkpoint/SKILL.md).

- **Outputs/evidence:** valid owner/scope/next action and available evidence identified without old chat/temp; subsequent authorized reconciliation/checkpoint on the same task where needed. ## Explicit invocation adaptations (upstream bytes unchanged)

The shared envelope supplies Foundry integration, not an invisible edit to upstream methods:
- Readable-path loading replaces a Skill-tool instruction only for the accepted manual route. It does not fake a native load. Human-only entry points require explicit selection or covering delegation, including an upstream instruction to reach another human-only method.
- The accepted binding replaces upstream setup assumptions. Missing binding/access means stop for exact repair; do not run setup-matt-pocock-skills, select a local tracker or install another manifest implicitly. That optional utility is not bundled or required.
- Provider forms/labels/native identities govern publication, not unconditional ready-for-agent or wayfinder labels. No protected approval label is supplied. Identity-first creation precedes relation writes and readbacks.
- Durable decision recommendations may be adopted only within an actual recorded covering delegation; report them as assistant recommendations, never invented individual answers. Later human disagreement prevails.
- Applicable checks and confirmed native closeout follow implement's commit endpoint. Independent review remains required where the project requires it; serial review is labelled serial.

Optional orchestration (`implement-spec`) and automatic fresh-session continuation are not selected or bundled here. They need separately accepted recipes/capabilities/ownership/integration/isolation evidence, not a new runner or automatic chain. A human-started clean session can use foundry-resume; neither context disposal nor a new ID alone proves isolation. Optional utilities/stack skills not listed are external, explicitly selected prerequisites, not promised installed resources.
