# Repository integration foundation

Run `node start.mjs` first. Startup is passive: it diagnoses the installed foundation and proposes a next action; it does not launch work or grant authority. Read [the accepted binding](docs/bindings.md) and [the procedure index](.factory/procedures.md) before selecting work. [Provenance](.factory/provenance.json) identifies installed sources, configuration and scoped readiness evidence, not task status.

## Authority and work

- The human supplies goals, scope, consequential decisions and authorization. Invoke a human-only procedure only through explicit selection or a delegation covering that procedure and its effects; completion of one procedure does not select the next.
- The setup-bound tracker is the sole authority for change specifications, decisions, tasks, native ownership/dependencies/state, checkpoints and verification records. Git holds code and maintained documentation; exact primary evidence artifacts are linked from the tracker. Local notes, chat and installer state are not alternative task stores.
- For an existing unit, first read fresh native identity, state, owner, parent/blockers and its explicitly canonical confirmed checkpoint. Load only relevant linked constraints. Retrieve exact prerequisite artifacts and verify integration before dependent work; closure alone is insufficient. Silence is not ownership transfer.
- Before consequential action, identify the workspace, actual execution location, path/network/credential reach and accepted destination/effects. Tool availability and a sandbox label are not authorization. Defer only the affected unauthorized action; never inspect or publish credentials.
- Use small applicable procedures and observable criteria, not a compulsory phase engine. Investigations record question, sources, observations and conclusion; implementations require actual behavior checks and appropriate review. Commit, PR or issue closure alone is not verified completion or integration.
- Confirm every durable create, claim, update, relation, checkpoint, status change and completion, then freshly read back the exact native target and intended content/state. Malformed, mismatched, unavailable or uncertain results remain unconfirmed. Inspect the exact target before retrying an unknown effect; never replay blindly or fall back to local task files.
- Routine effects must be within the delegation and current project gates. No procedure supplies protected approval, review approval, merge, deployment, migration/deletion, publication, external configuration or expanded scope. Stop the affected action at the exact missing decision/permission/evidence. Independent authorized work continues only with demonstrated shared-state safety.

## Continuity and completion

Use [foundry-checkpoint](.factory/skills/foundry-checkpoint/SKILL.md) at a recoverable milestone, interruption, transfer or blocker. Use [foundry-resume](.factory/skills/foundry-resume/SKILL.md) for cold continuation. Preserve actual work artifacts before disposing of context. Local-only progress is valid but is not transfer-ready.

Completion requires the accepted criteria, applicable exercised checks/review, retrievable exact artifacts and confirmed native closeout. Name missing evidence and the next owner/action instead of claiming Done. Review results bind their exact base/head and full diff; serial review never claims independence. Required independent review remains a gate.

Direct bounded manual work is the baseline. Orchestration and automatic fresh-session continuation require separate explicit selection, real capability/control/isolation evidence and safe integration ownership. Neither is started by installation or startup. A subagent, fork or resumed transcript is not a genuinely new session. Optional modes not selected are not baseline failures; a failed required route cannot silently downgrade.
