## Reusable product boundary inventory

1. **Core packaged creator is a bounded CLI, not merely a prompt.** `package.json:2-20,43-46` declares the scoped package, `foundry` binary, Node floor, pnpm version, and MIT license. `src/creator.ts:29-33,76-100,133-171` defines versioned manifest/state, explicit lifecycle categories (`removed`/`inherited`/`generated`), and structured operation/diagnostic/envelope types. `docs/creator.md:3-12,118-136` describes plan/dry-run/apply/verify/doctor and creator-owned state. The architecture gives a plausible reusable seam: packaged immutable template input + config resolution/composition + plan/apply/verification engine, independently of any one agent harness.
2. **Ownership/composition boundary is unusually explicit and transferable as a model.** `archetype-ownership.json:1-3,4-69` enumerates text render candidates; `MAINTAINERS.md:13-30` distinguishes removed governance and provider/CI inputs from inherited assets and generated outputs and requires inventory registration. `docs/factory-layout.md:8-52` specifies root vs `.factory/` support, generated root outputs, and source-only input removal. In code, `src/creator.ts:1002-1055` filters removed paths, relocates inherited entries, composes outputs and errors on unclassified payload items. This lifecycle separation is a reusable design/concrete inventory, but its exact path policy may conflict with a smaller product that wants fewer inherited docs/process assets.
3. **Conflict-safe updates, evidence, and recovery.** Creator docs state target unknowns are not overwritten, unchanged reruns are `noop`, config changes produce a plan, and external drift becomes conflict; state stores payload/config identity and owned output digests (`docs/creator.md:118-136`). Source `src/creator.ts:1058-1077,1172-1181,1245-1282` detects invalid/interrupted/payload-mismatched state, unknown files and symlink/drift conditions. `docs/determinism.md:7-20,22-45` declares offline read-only plan/verify/doctor, transactional apply, repeatability and boundary checks. `docs/creator.md:159-161` identifies deterministic failure injection and doctor recovery. This is a reusable safety mechanism, though consumers inherit a particular state schema, namespace `.factory-template-creator`, plan/status vocabulary and lifecycle semantics unless deliberately migrated.
4. **Provider adapters are data/catalog-driven and workspace-scoped.** `providers/agents/catalog.json:1-73` names Claude Code, OpenCode, Codex, and Pi with executable, workspace file, argv template, manual installation/auth prerequisites and explicit handoff capability. `docs/creator.md:86-116` says no provider is default, selection is explicit, executable availability is checked before writes, only selected owned workspace files are generated, and agent launch is opt-in and shell-free after successful apply/verify; global preferences/auth/model config remain manual. This is concrete harness adapter material, not interchangeable slash-command skills: templates are instructions, catalog records output path and launch args, and adapters do not install/authenticate harnesses.
5. **Creator UX and machine interface are separable.** `docs/installer-ux.md:3-21,29-71` says terminal rendering delegates all changes to same engine; stdout is one versioned JSON envelope, human prompts/progress/diagnostics on stderr, confirmation defaults no, and cancellation/failures have explicit outcomes. Source `src/index.ts` defines CLI parsing/command boundary (local source lines 48 onward; file was not fully line-read, so no finer claim). This separation could be retained without retaining the full interface policy.
6. **Offline external-factory pinning and reusable CI composition.** `docs/creator.md:14-59,61-84` describes optional explicit local checkout plus independently trusted full SHA, clean checkout/tag/default checks, external config separation, key-resolution precedence, and offline workflow composition. It explicitly limits proof: cannot prove remote publication/GitHub acceptance; step-job `runs-on` validation is separate. This is an advanced feature and material scope/cost, not a generic prerequisite for a Matt-first setup.
7. **Release and real-agent test machinery are substantial but mostly source-governance.** `MAINTAINERS.md:13-22,43-67,122-149` classifies release/template E2E, provider recipes, ownership inputs as source-only/removed; reusable initialized project assets are separated. `docs/real-agent-journey.md:7-69,70-85` describes runtime catalog, run-scoped provisioning, cold Codex execution, independent assertions and bounded evidence. These workflows/evidence helpers demonstrate concrete prior work but are not necessarily downstream product assets.

## Incompatibilities and concrete evolution constraints (facts, not recommendation)

- The source's top-level operating contract is a language-agnostic archetype with strict one-ticket-per-session, ordered gated phases, tracker-specific exclusive task state, durable handoffs and protected human approval (`AGENT.md:38-52,54-93,95-110`). This is stronger and more prescriptive than small adaptable procedures; if the target avoids process-owning framework behavior, these are product-contract decisions to scope, not mere copy edits.
- Creation owns a repo-wide template layout, ownership inventory, `.factory/` relocation, generated bindings/CI, provider/CI composition, cleanup and schema/state compatibility. Existing initialized repositories are not migrated automatically; layout docs explicitly say manual reviewed moves and no migration command (`docs/factory-layout.md:54-62`). Reusing creator internals therefore carries more than importing reusable helper functions: it couples to lifecycle/path/output contracts.
- The source does not install or globally configure harnesses, credentials, models, or agent binaries. Runtime startup is a separately explicit handoff; repository setup success is distinct from agent success (`docs/creator.md:99-116,138-142`; `docs/installer-ux.md:23-32`). Any desired install flow must consciously preserve or change this line.
- Root files and host-discovered paths are compatibility constraints (`docs/factory-layout.md:14-30,87-100`): `AGENT.md`, `CLAUDE.md`, `README.md`, `start.mjs`, `.github/`, host config dirs and generated bindings are kept at root; generic docs/hooks/templates move under `.factory`; providers/CI/maintainer tooling are removed. Replacing only the docs while retaining adapters or creator likely leaves a mismatch between declared ownership and generated shape.
- Release continuity is tied to package/bin identity and immutable npm versions. Local `package.json:2-20` declares `@eff3ct/agent-foundry` and `foundry`; release workflow `.github/workflows/npm-release.yml:1-18,37-86,88-168` resolves exact tag SHA/version, builds/packs that SHA once, validates local identity, claims publication, reads back registry metadata/tarball/payload and stores 7-day evidence. `MAINTAINERS.md:45-67` states npm versions are immutable and rollback requires corrected version; Template mode is a separate safety valve. Retaining this repo entails preserving those external contracts or explicit migration; replacement would forgo the existing name/history/release pipeline unless separately transferred. These are consequences, not a keep/replace judgment.
- The published release is at `dd04262…`, not local `3e1267d…`; behavior in source files added after release cannot be attributed to the published installer based on the available evidence. The release note establishes the v0.3.1 current-directory `npm create` fix and pair publication, not all details of installer internals.

## Decision value and new-specifiability

The evidence makes an evolution-vs-replacement discussion concrete: candidate assets include transactional conflict-safe creator, ownership lifecycle/composition, four workspace adapters, offline verification and release identity pipeline; costs include a large, strongly governed archetype contract, stable generated layout/state/package identity, old-target manual migration, and separate source-only governance. It does **not** establish which benefits outweigh costs.

No genuinely new product decision question is required: the existing repository-strategy ticket #399 already asks exactly whether to evolve, replace, or preserve selected assets and asks about concrete benefits and preservation boundaries. The installation, contract-boundary, resumption, and command tickets cover adjacent choices. This research authorizes neither archival nor strategy selection.
