# Matt Pocock skills compatibility and distribution facts

Research snapshot: upstream `mattpocock/skills` main at [`49dd158d1076134a641b33efb035946536778336`](https://github.com/mattpocock/skills/tree/49dd158d1076134a641b33efb035946536778336) (observed with `git ls-remote` on 2026-10-14). Sources below are pinned to that commit; repository statements describe documented/prompt behavior, not runtime guarantees.

## Upstream philosophy and procedure fit

The README explicitly rejects process-owning frameworks on grounds of loss of user control and hard-to-resolve process bugs; it describes skills as small, adaptable, composable, model-agnostic, and invites adaptation. `SCOPE.md` requires reports of observed failures and rejects config options or harness-specific branches intended for one workflow; such customization belongs in project `CLAUDE.md`/`AGENTS.md` or an editable skills.sh fork. [README](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/README.md), [SCOPE.md](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/SCOPE.md).

The upstream sequence is conditional, not a mandatory universal pipeline. `to-spec` records already-made decisions as one tracker issue; it does not interview/decide. It is for multi-session work; a single-session change goes straight to `implement`. `to-tickets` may split spec or current conversation into tracker tickets, each intended as a tracer-bullet slice for a fresh context; it requires tracker setup and explicit human approval of proposed decomposition before publication. `implement` executes one ticket, drives tests/typechecks/review, commits on the current branch, but does not close/update the ticket or verify acceptance checkboxes. These are specified instructions, not guarantees that a model follows them. [to-spec](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/docs/engineering/to-spec.md), [to-tickets](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/docs/engineering/to-tickets.md), [implement](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/docs/engineering/implement.md).

`implement-spec` is an optional one-run orchestrator: it consumes the spec plus ticket dependency graph, delegates ready-frontier tickets into worktrees, integrates/reviews, and resolves tickets; it requires background subagents and worktree support. This does not equate to the human-confirmed Foundry goal of one unit per session, but is an explicit optional alternative, not upstream's only workflow. `handoff` writes a portable summary to OS temp, not durable project storage; the doc specifically warns temp may disappear across sessions/reboots (Codex reported), and says durable copies must be made by user when needed. Thus upstream handoff alone is not a durable cold-resume authority. [implement-spec](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/docs/engineering/implement-spec.md), [handoff](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/docs/productivity/handoff.md).

Setup is prompt-driven, asks for confirmation, writes repo-local markdown tracker/domain configuration, and has no global mode; user edits are possible. Its tracked configuration is consumed by skills but is prose, not a durable-provider enforcement mechanism. [setup](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/docs/engineering/setup-matt-pocock-skills.md). Invocation rules distinguish user-invoked from model-invoked through per-harness skill metadata. Human-only is explicitly configured (`disable-model-invocation` for Claude, `allow_implicit_invocation:false` for Codex); dependent skills use Skill tool calls for model-invokable skills. This is stronger harness metadata gating, but descriptions/procedures remain prompts and do not mechanically guarantee phase transitions or persistence. [invocation](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/.agents/invocation.md).

## Foundry contract comparison

Foundry source template `AGENT.md` requires all task state in the bound provider, provider-confirmed fresh readback for durable updates, phase handoff with exact next action/branch/verification, one work unit per session, and no completion without required gates. The generic source `docs/bindings.md` says it is a template, not a concrete initialized provider; the current checkout is SELF mode. These are Foundry declarations, not proof of runtime enforcement. [AGENT.md lines 38-47, 71-93](https://github.com/eff3ct0/agent-foundry/blob/dd04262d1076134a641b33efb035946536778336/AGENT.md), [bindings.md lines 1-19](https://github.com/eff3ct0/agent-foundry/blob/dd04262d1076134a641b33efb035946536778336/docs/bindings.md).

Compatibility facts: upstream's human approval before ticket creation and invocation distinctions can be reused as procedure conventions. Its `to-spec` tracker issue can coexist with Foundry's ticket authority in principle, but its assumptions that specs are snapshots/disposable after shipping and handoff is a transient temp artifact differ from Foundry's durable, read-back authoritative task state. Setup's editable repo markdown can describe trackers yet does not itself supply the Foundry provider confirmation/readback contract. `implement`'s commit-only endpoint leaves tracker closeout to operator, while Foundry requires provider updates/checkpoint evidence. These are observable contract differences; they do not establish whether adaptation or replacement is preferred.

The separation between descriptive prose and mechanics is important: upstream guides prescribe interaction and file writes; invocation metadata can suppress auto-invocation in supported harnesses. Neither source promises identical model output or a universal guarantee of repository-bound persistence. Foundry's own agent-authored contracts likewise need implementation/provider evidence before claiming enforcement.

## Installation, discovery, updates, licensing

Pinned upstream README lists managed plugin installation for Claude, Codex, Copilot, and VS Code; Gemini CLI copies engineering/productivity directories and requires rerunning install commands; skills.sh copies selected editable files and requires `npx skills@latest update` plus re-running `add` for new skills. It says plugin and editable skills.sh routes should not both be installed because they duplicate skills. Exact README routes and qualifications: [pinned README](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/README.md). Detailed install source says plugins are managed/read-only, whereas skills.sh content is copied/editable; version changes and auto-updates depend on host behavior. Its own route table says Auggie, Droid, Qwen, Goose not tested; Copilot schema documented but not run. These are upstream's documented facts, not independently exercised installs. [install block](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/.agents/install-block.md).

README's skills.sh command targets harness-specific locations, while Foundry is explicitly repository-bound for task state and cold start. Skill discovery and slash-command syntax vary by harness; upstream explicitly frames Skill tool invocation as the cross-harness dependency convention. No source here establishes a single installation/discovery mechanism spanning all harnesses or a lockfile/version pin for skills.sh installs. The commit pin in this report is research reproducibility, not an upstream consumer version policy.

## Unresolved product choices / remaining question

This evidence informs, but does not settle, the existing boundary and command/skill-ownership questions: whether Foundry requires provider-authoritative phase checkpoints alongside upstream prompts; which transient handoff use cases merit a durable projection; whether to include optional `implement-spec` concurrency; and whether to use managed plugin or editable skills files by harness. Human choice remains required. No additional decision question is justified: the existing installation, boundary, resumption, and commands tickets already cover these tradeoffs.
